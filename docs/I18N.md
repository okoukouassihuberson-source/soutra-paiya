# Multilingue — guide technique

SOUTRA PLAYCE est disponible en **français** (langue d'origine, URLs inchangées) et en **anglais** (`/en/…`).
L'architecture accepte l'espagnol, l'italien, le portugais et l'arabe (RTL) : il suffit d'ajouter un dictionnaire.

## Comment ça marche
| Élément | Fichier |
|---|---|
| Langues déclarées, activation, direction (ltr/rtl), format | `apps/web/lib/i18n/config.ts` |
| Routage : `/en/x` est réécrit vers `/x` avec l'en-tête `x-locale` (non falsifiable) | `apps/web/middleware.ts` |
| Dictionnaires typés (clés vérifiées à la compilation) | `apps/web/lib/i18n/dictionaries/{fr,en}.ts` |
| `t`, `tn` (pluriels), `tdyn` (libellés issus de la base), `field`/`list` (contenu éditorial), `lp` (lien localisé), formats | `apps/web/lib/i18n/t.ts` |
| Serveur : `getI18n()` — Client : `useI18n()` | `server.ts`, `client.tsx` |
| hreflang / canonical / Open Graph | `apps/web/lib/i18n/seo.ts`, `app/sitemap.ts` |
| Sélecteur de langue (mémorise le choix dans un cookie) | `components/tourism/LanguageSwitcher.tsx` |

Règles : le français reste à la racine (aucune URL existante ne change) ; seul `/` redirige vers `/en` si le cookie `soutra_locale=en` est présent ; les pages `noindex` (recherche filtrée, comptes) ne portent pas de hreflang.

## Ajouter une langue (ex. espagnol)
1. `config.ts` : passer `es.enabled` à `true`.
2. Créer `dictionaries/es.ts` : `export const es: Dict = { … }` (le compilateur liste toutes les clés manquantes), l'enregistrer dans `dictionaries/index.ts`.
3. Rien d'autre : le middleware, le sélecteur, les hreflang et le sitemap se mettent à jour seuls. Une langue activée sans dictionnaire retombe sur l'anglais.
4. Arabe : `dir="rtl"` est déjà posé sur `<html>` ; vérifier visuellement les composants (marges `ml-/mr-` à remplacer par `ms-/me-` au fil de l'eau).
5. Lancer `pnpm --filter @soutra/web test:i18n` (parité des clés et des `{paramètres}` entre toutes les langues).

## Modifier un texte
Éditer la clé dans `fr.ts` **et** `en.ts` (même clé, mêmes `{paramètres}`). Une clé inconnue est une erreur de compilation.

## Contenu éditorial (base de données)
Destinations, voyages, programme, formules et activités ont une colonne `i18n jsonb` (migration 0090) :
`{ "en": { "title": "…", "description": "…" } }`. Les champs vides retombent sur le texte français.
Les éditeurs (admin et organisateur) ont un bloc « 🌐 Traduction » par langue active. Les listes (inclus, activités…) sont saisies une entrée par ligne.
La recherche d'activités interroge aussi les titres traduits.

## Périmètre actuel (honnêteté)
Traduit : accueil (portail touristique), navigation, Explorer (filtres, carte), destinations, voyages, activités, réservations et paiements, billets, avis, notifications (pages et préférences), métadonnées SEO.
**Non traduit (français uniquement)** : sections marketing de l'accueil (masquées en anglais), fiche établissement `/v/[slug]`, connexion, `/account`, `/pro`, `/admin`, espace organisateur, scan de billets, fidélité, abonnements, **texte des notifications** (généré en français côté base), emails de notification, application mobile.

## Application mobile
Voir `apps/mobile/lib/i18n/`. Même principes que le web (dictionnaires typés, repli sur le français, contenu éditorial `i18n`), sans routage par URL. Le français est la langue par défaut ; l'anglais est **opt-in** (Paramètres → Langue) tant que l'app historique n'est pas entièrement traduite (`pnpm --filter @soutra/mobile i18n:todo`). Pour traduire un écran : remplacer les textes par `t('clé')` (`const { t } = useI18n()`), ajouter la clé dans `fr.ts` **et** `en.ts` (le compilateur signale l'oubli), utiliser `tr()` hors composants.
